# LOAD-BALANCER.md
## ロードバランサー（負荷分散・セッション維持・死活監視・DSR・GSLB）

***

## ロードバランサーの基本機能

| 機能 | 内容 | 例 |
| --- | --- | --- |
| **負荷分散**機能 | 通信をどのようにバックエンドの機器に振り分けるか決定する機能 | IPベース, TCP/UDPベース, URLベース … 等 |
| **セッション維持**機能（**セッションアフィニティ**機能とも） | クライアントからの通信を、アプリケーションの仕様に応じて同じバックエンド機器に振り分ける機能 | IPのハッシュ値ベース, Cookieベース … 等 |
| **死活監視**機能 | バックエンド機器の稼働状況を監視するための機能。ダウンした機器については振り分け対象から動的に外すことが可能 | TCPプローブ, HTTPプローブ … 等 |

死活監視用の通信を「**プローブ**」と呼ぶことがある。

## セッション維持機能

アプリケーションによっては後続の通信が同じサーバーに振り分けられる必要がある。その際、何らかの**セッション維持（セッションアフィニティ）機能**が必要となる。

| セッション維持方式 | 詳細 |
| --- | --- |
| **IPベース** | 同じ**送信元IPアドレス**からの通信を同じサーバーに振り分ける |
| **Cookieベース** | Cookieに埋め込まれた**セッションID**を基に通信を同じサーバーに振り分ける |
| URLパラメーターベース | URLに含まれるパラメーター（例: `session_id=123`）を基に同じサーバーに振り分ける。※セキュリティ上の懸念があるため、あまり一般的ではない |

### SSL/TLS アクセラレーター機能

* バックエンドの**サーバーに代わり、SSL/TLS通信を終端する**機能
* **HTTPS通信の中身が確認可能**となるため、**Cookieベースのセッション維持等で併せて利用**される

## 死活監視機能

バックエンドサーバーのダウンを検知するために定期的な死活監視が必要。死活監視に失敗したサーバーを動的に振り分け対象から除外できる。

| 死活監視方式 | 詳細 |
| --- | --- |
| **ICMPプローブ** | サーバーに定期的にPingを送信し、応答がない場合ダウンとみなす（ICMPはL3レイヤー） |
| **TCP/UDPプローブ** | サーバーの特定ポートとTCP/UDP通信を試み、応答がない場合ダウンとみなす（TCP/UDPはL4レイヤー） |
| **HTTP/HTTPSプローブ** | サーバーとHTTP/HTTPS通信を試み、応答の有無やステータスコードによってダウンとみなす（HTTP/HTTPSはL7レイヤー） |

ICMPやTCP/UDPではWebアプリケーションの詳細な稼働状況までは判断できない（例: Pingには応答できるが、Webサーバーはダウンしている … 等）。そのため、**より正確にWebアプリケーションの稼働状況を監視するには、HTTP/HTTPSプローブを利用する必要がある**。ロードバランサーによってはその他のプロトコルや方式による死活監視をサポートする。

## ワンアーム構成

* ロードバランサーに直接バックエンドサーバーを接続せず、**ネットワークを介して間接的に接続**する方式
* LBの追加や交換がしやすく**スケーラビリティに優れる**
* 大規模なシステムや負荷が高い環境で有効、システムの**パフォーマンスと可用性**を確保するのに適する

例）Client →（宛先=10.0.0.100）→ スイッチ → Load Balancer (IP: 10.0.0.100) → スイッチ →（宛先=10.0.0.1）→ Server01: 10.0.0.1 / Server02: 10.0.0.2

## DSR (Direct Server Return)

* ワンアーム構成において、**戻りの通信をLBを経由せずに直接クライアントに返す**方式
* インライン構成/ワンアーム構成のどちらも**原則 行きと戻りの通信がLBを経由**するが、**ワンアーム構成にてDSR方式**を採用することで、戻りの通信を直接クライアントに返せる
  * メリット: LBを経由する通信が減ることによる**パフォーマンス向上**
  * デメリット: **SSL/TLSアクセラレータ機能**が利用できないため暗号化通信処理が難しくなる、構成が少々複雑

**DSRの例:** LBはNATをせず振り分けのみ実施。

| 通信 | 宛先 / 送信元 |
| --- | --- |
| Client (192.168.0.1) → LB | 宛先 = 10.0.0.100 |
| LB → Server | 宛先 = **10.0.0.100**（NATしない） |
| Server → Client（LBを経由しない） | 宛先 = 192.168.0.1、**送信元 = 10.0.0.100** |

バックエンドサーバー（Server01: 10.0.0.1 / Server02: 10.0.0.2）は **LBの持つIP (10.0.0.100) を Loopback Interface 等で保有**し、自身宛の通信として受信/応答する。

**Loopbackアドレスの設定が必要な理由:**
* **LBのIPアドレスを認識するため**: サーバーはLBのIPアドレスを直接保持していないため、**LoopbackにVIPを設定して自分宛ての通信として処理**する必要
* **非対称通信の対応**: リクエストはLBを経由するが、レスポンスは直接クライアントに返される。そのため、**LBのIPアドレスを使った戻りの通信**が必要

## GSLB (Global Server Load Balancing)

* **ユーザーに最も近いエッジサーバーを判断**し、そこにアクセスさせるための負荷分散の仕組み
* **DNSベース**のGSLBが一般的
  * 例: 送信元IPアドレスを基にクライアントの国を判断し、その国のエッジサーバーのIPアドレスを応答

**流れ（日本のクライアントの場合）:**
1. DNSサーバーは名前解決要求の送信元IPアドレスを基に日本のクライアントと判断
2. 日本のエッジサーバーのIPアドレスを応答
3. クライアントは日本のエッジサーバーにアクセス
