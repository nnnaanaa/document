# OPS-MONITORING.md
## 運用・監視 暗記シート

***

## ひとことで

監視は、「**動いているか**」「**どれだけ使われているか**」「**何が起きたか**」を、それぞれ別のしくみで見る。午後の後半では、**どのしくみで何が分かるか**と、**障害の原因をどう絞り込むか**が問われる。

| 見たいこと | 使うもの | 分かること |
| --- | --- | --- |
| **動いているか**（死活監視） | **ping**（ICMP） | 機器に IP で届くか |
| サービスが動いているか | TCP のポートへの接続、HTTP の応答の確認 | アプリケーションが応答するか |
| **どれだけ使われているか** | **SNMP** のポーリング | 通信量、CPU 使用率、エラーの数など |
| **異常が起きた瞬間** | **SNMP トラップ** | リンクダウンなどの発生 |
| **何が起きたか**（記録） | **Syslog** | 機器が出したログ |
| **誰が何の通信をしているか** | **フロー情報**（NetFlow・IPFIX・sFlow） | 送信元・宛先・ポートごとの通信量 |
| **通信の中身** | **ミラーポート**でのパケットキャプチャ | 実際のパケット |

## SNMP

**SNMP**（Simple Network Management Protocol）は、機器の状態を**取得・設定・通知**するプロトコル。

```mermaid
flowchart LR
  M["SNMP マネージャ<br>（監視サーバ）"] -- "ポーリング　UDP 161" --> A["SNMP エージェント<br>（機器）"]
  A -. "トラップ　UDP 162" .-> M
```

| 用語 | 内容 |
| --- | --- |
| **マネージャ** | 監視する側（監視サーバ） |
| **エージェント** | 監視される側（ルータ、スイッチ、サーバ） |
| **MIB** | エージェントが持つ**管理情報の集まり**。項目は木の形に整理され、**OID**（番号の並び）で指定する |

### ポーリングとトラップ

| 方式 | 向き | ポート | 特徴 |
| --- | --- | --- | --- |
| **ポーリング** | マネージャ → エージェント（**定期的に問い合わせる**） | **UDP 161番** | 値の変化を継続して記録できる。**次の問合せまで異常に気付けない** |
| **トラップ** | エージェント → マネージャ（**異常時に自分から通知**） | **UDP 162番** | **すぐに分かる**。UDP なので、**届かなくても再送されない** |

- 両方を**組み合わせる**: トラップですぐに知り、ポーリングで取りこぼしを補う
- 機器が**完全に止まる**と、トラップも送れない → ポーリング（や ping）で気付く

| メッセージ | 内容 |
| --- | --- |
| GetRequest / GetNextRequest | 値を取得する / 次の項目の値を取得する |
| GetBulkRequest | 多くの値をまとめて取得する（v2c から） |
| SetRequest | 値を設定する |
| **Trap** | 異常の通知（**確認応答なし**） |
| **InformRequest** | 異常の通知（**確認応答あり**。届かなければ再送する。v2c から） |

### バージョン

| バージョン | 認証 | 暗号化 |
| --- | --- | --- |
| v1 / **v2c** | **コミュニティ名**（平文のパスワードのようなもの） | **なし** |
| **v3** | **利用者ごとの認証** | **あり** |

- v2c はコミュニティ名が**平文で流れる** → **v3 を使う**。v2c を使うなら、**問合せを受け付ける送信元をマネージャの IP アドレスに限定**し、初期値（public）を変える

### 通信量の計算

インタフェースの通信量は、MIB の**カウンタ**（機器が起動してからの**累積のバイト数**）で分かる。

**通信量（bps）＝（今回の値 − 前回の値）× 8 ÷ 取得の間隔（秒）**

例）5分（300秒）間隔で取得し、差が 750,000,000Byte → 750,000,000 × 8 ÷ 300 ＝ **20Mbps**

- 求まるのは、その間隔の**平均**。**短時間だけの混雑（バースト）は平均に埋もれて見えない** → 間隔を短くする
- 32bit のカウンタは約 43億で**一周して 0 に戻る**。高速な回線では、取得の間隔の間に一周してしまう → **64bit のカウンタ**を使う

## Syslog

機器の**ログを、ネットワーク経由でログサーバへ送る**しくみ（**UDP 514番**。TCP や TLS で送る方式もある）。

| 項目 | 内容 |
| --- | --- |
| **重大度**（Severity） | **0（緊急）〜 7（デバッグ）**の8段階。**数字が小さいほど重大** |
| ファシリティ | ログの種類（どの機能が出したか） |

**ログサーバに集める理由**

- 機器の中のログは、**容量が小さく、再起動で消える**ことがある
- 機器が侵入されても、**ログを消されたり書き換えられたりしにくい**
- 複数の機器のログを、**時刻で並べて突き合わせ**られる

## NTP

**機器の時刻を合わせる**プロトコル（**UDP 123番**）。

- **stratum**（階層）: 基準の時計が 0、そこに直接つながるサーバが **1**。**数字が小さいほど基準に近い**
- 社内に NTP サーバを置き、**社内の機器はすべてそこに合わせる**

| 時刻がずれると困ること | 内容 |
| --- | --- |
| **ログの突合せ** | 複数の機器のログを並べても、**前後関係が分からない** |
| 証明書の検証 | 有効期間の判定を誤る |
| 認証 | Kerberos は、時刻が**5分以上ずれると失敗**する |

## フロー情報

ルータやスイッチが、通信を**フロー**（送信元 IP アドレス・宛先 IP アドレス・送信元ポート・宛先ポート・プロトコルの組）ごとにまとめて、**コレクタへ送る**。

| 方式 | 特徴 |
| --- | --- |
| NetFlow | シスコが作った方式 |
| **IPFIX** | NetFlow を基にした**標準規格** |
| sFlow | パケットを**一定の割合で抜き出して**（サンプリング）送る。機器の負荷が小さい |

- SNMP で分かるのは**インタフェース全体の通信量**まで。**「誰が、どこと、何の通信で」帯域を使っているか**は、フロー情報で調べる

## ミラーポートとパケットキャプチャ

**ミラーポート**（ポートミラーリング）は、スイッチの**指定したポートを通るフレームのコピー**を、別のポートへ出す機能。そこに**パケットキャプチャの装置や IDS** をつなぐ。

| 注意点 | 内容 |
| --- | --- |
| **取りこぼし** | 送信と受信の**両方をコピー**すると、最大で**元のポートの2倍**の量になる。ミラーポートの帯域を超えた分は**捨てられる** |
| スイッチの負荷 | コピーの処理で負荷が増える |
| エラーフレーム | スイッチが捨てたフレームは、コピーされない |

- **ネットワークタップ**: ケーブルの途中に入れて**信号を分岐**する装置。取りこぼしがなく、エラーフレームも見える。設置のときに**リンクが一度切れる**

## LLDP

**隣につながっている機器の情報**（機器名、ポート、VLAN など）を、L2 で知らせ合うプロトコル（IEEE 802.1AB）。

- **どのポートに何がつながっているか**を、配線をたどらずに確認できる → 構成図との照合、配線の誤りの発見
- IP 電話機などに、VLAN や PoE の情報を伝える拡張（LLDP-MED）もある

## ICMP と切り分けの道具

| 道具 | しくみ | 分かること |
| --- | --- | --- |
| **ping** | **Echo Request**（タイプ 8）を送り、**Echo Reply**（タイプ 0）を待つ | 相手まで IP で届くか、往復の時間 |
| **traceroute** | **TTL を 1 から順に増やして**送る。TTL が 0 になったルータが返す **Time Exceeded**（タイプ 11）から、経路上のルータを順に知る | **どこまで届いているか**、どの経路を通るか |

| ICMP のメッセージ | 意味 |
| --- | --- |
| Destination Unreachable（タイプ 3） | 届けられない（経路がない、ポートが閉じている、**分割が必要だが DF ビットが立っている**、など） |
| Time Exceeded（タイプ 11） | TTL が 0 になった |
| Redirect（タイプ 5） | 「もっとよいゲートウェイがある」と送信元に知らせる |

- **ICMP を FW ですべて止める**と、ping や traceroute が使えないだけでなく、**経路 MTU 探索も失敗**する

## 障害の切り分け

**下の層から順に**、また**近いところから順に**確かめる。

| 層 | 確かめること | 道具 |
| --- | --- | --- |
| 物理層 | ケーブル、**リンクランプ**、インタフェースの状態、**エラーの数** | 機器の表示、SNMP |
| データリンク層 | **VLAN の設定**、**MAC アドレステーブル**、STP の状態、ループの有無 | 機器のコマンド |
| ネットワーク層 | IP アドレスとデフォルトゲートウェイ、**ARP テーブル**、**ルーティングテーブル** | **ping**、**traceroute** |
| トランスポート層より上 | ポートが開いているか、**FW のログ**、**名前解決**、アプリケーションのログ | ポートへの接続、nslookup / dig |

**絞り込みの問い**

- **いつから**起きているか（その前に**何を変更したか**）
- **どの範囲**で起きているか（1台だけか、同じ VLAN の全部か、同じ拠点の全部か）
- **何ができて、何ができないか**（ping は通るが Web が見えない、IP アドレスなら通るが名前では通らない、など）

| 症状 | 疑うところ |
| --- | --- |
| IP アドレスでは通信できるが、**名前ではできない** | **DNS** |
| ping は通るが、アプリケーションが使えない | **FW のルール**、サーバのサービス、ポート |
| 小さいデータは通るが、**大きいデータが通らない** | **MTU**（分割と DF ビット、ICMP の遮断） |
| **つながるが遅い**、エラーの数が増えている | **通信方式の不一致**（片方が固定の全二重、もう片方が自動設定 → 自動側が**半二重**になる） |
| 同じ VLAN の全体が通信できない、スイッチのランプが激しく点滅 | **ループ**（ブロードキャストストーム） |
| 行きは届くが、戻りが届かない | **戻りの経路**（ルーティング）、非対称な経路と FW |
| 機器を交換した直後だけ通信できない | 周りの機器の **ARP テーブル・MAC アドレステーブル**に古い情報が残っている |

## 機器の管理

| 項目 | 内容 |
| --- | --- |
| 管理用の接続 | **SSH**（TCP 22番）を使う。**Telnet（TCP 23番）は平文**なので使わない |
| **管理用ネットワークの分離** | 管理の通信を、利用者の通信とは**別の VLAN・別の回線**にする。利用者の通信が止まっても、機器に入れる |
| 接続元の制限 | 管理用の端末（踏み台サーバ）からだけ受け付ける |
| 操作の記録 | **誰が、いつ、何をしたか**を残す（利用者ごとの ID で認証する。共用の ID は使わない） |
| 設定のバックアップ | 変更の前後で設定を保存し、**元に戻せる**ようにする |

**作業の進め方**

- 作業の前に、**手順・確認の方法・元に戻す手順（切戻し）**を決めておく
- 冗長構成の機器は、**片方ずつ**作業する（予備側から始め、切り替えて確かめてから、もう片方）
- 作業の前後で、**同じ確認**（ping、経路、インタフェースの状態）を行って比べる

## 試験でよく問われるポイント

### SNMP

| 論点 | 覚えること |
| --- | --- |
| ポート | **ポーリングは UDP 161番**（マネージャから）、**トラップは UDP 162番**（エージェントから） |
| トラップの弱点 | **届かないことがある** → ポーリングと組み合わせる。確認応答が要るなら **InformRequest** |
| バージョン | **SNMPv3 は認証と暗号化がある**。v2c のコミュニティ名は平文 |
| 通信量の計算 | **カウンタの差 × 8 ÷ 間隔**。平均なので、**バーストは見えない** |

### ログ・時刻

| 論点 | 覚えること |
| --- | --- |
| Syslog | **UDP 514番**。ログサーバに集め、**NTP で時刻を合わせる** |

### 通信の調べ方

| 論点 | 覚えること |
| --- | --- |
| 誰が帯域を使っているか | SNMP ではなく**フロー情報**で調べる |
| ミラーポート | **取りこぼし**に注意する |
| traceroute | **TTL を増やしながら**、Time Exceeded を集める |

### 答えの型

| 問われ方 | 答えの型 |
| --- | --- |
| SNMP トラップだけの監視では不十分な理由 | 「UDP で送られ、**届かなくても再送されない**から」「機器が停止すると、**通知そのものを送れない**から」 |
| SNMP ポーリングだけの監視では不十分な理由 | 「**次の取得までの間**に起きた異常を、すぐに検知できないから」 |
| SNMP の5分間隔の平均では分からないこと | 「**短時間の通信量の急増**（バースト）」 |
| v2c と比べて SNMPv3 にする理由 | 「v2c は**コミュニティ名が平文**で流れ、盗聴されると機器の情報を読まれるから」 |
| ログを Syslog サーバにも送る理由 | 「機器が侵入・故障しても、**ログが消えたり改ざんされたりしない**ようにするため」 |
| 全機器の時刻を NTP で合わせる理由 | 「複数の機器の**ログを時刻で突き合わせ**られるようにするため」 |
| SNMP ではなくフロー情報で分かること | 「**どの端末が、どの宛先と、どのアプリケーションで**通信量を使っているか」 |
| ミラーポートのキャプチャで取りこぼす理由 | 「送信と受信の両方をコピーすると、**ミラーポートの帯域を超える**ことがあるから」 |
| 管理用の通信を別のネットワークにする理由 | 「利用者の通信に障害があっても、**機器に接続して調べられる**ようにするため」 |
| 冗長構成の機器を片方ずつ更新する理由 | 「作業中も**もう片方で通信を続け**、問題があればすぐに戻せるようにするため」 |
