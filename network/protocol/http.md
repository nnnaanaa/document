# HTTP.md
## HTTPステータスコード・ヘッダー・認証

***

## 代表的なHTTPステータスコード

| ステータスコード | 説明 |
| --- | --- |
| 100 Continue | リクエストを受理し、引き続き処理が継続可能であることを示す |
| 200 OK | リクエストを受理し、正常に処理されたことを示す |
| 301 Moved Permanently | リクエストを受理し、恒久的に別のページへリダイレクトすることを示す |
| 302 Found | リクエストを受理し、一時的に別のページへリダイレクトすることを示す |
| **400 Bad Request** | クライアントのリクエスト内容が無効であることを示す |
| **401 Unauthorized** | クライアントから提供された認証情報が無効であることを示す |
| **403 Forbidden** | クライアントの権限が不足していることを示す |
| **404 Not Found** | クライアントからリクエストされたリソースが存在しないことを示す |
| 429 Too Many Requests | クライアントが短期間にリクエストを送りすぎており、**レートリミット**を超えていることを示す。APIやWebサービスで利用され、リクエスト数の制限がある場合に返却される |
| **500 Internal Server Error** | サーバー内部で予期せぬエラーが生じたことを示す |
| **502 Bad Gateway** | 経路中のゲートウェイやプロキシがサーバーから無効なレスポンスを受信したことを示す |

## HTTPヘッダーの種類

| 種類 | 説明 | 例 |
| --- | --- | --- |
| **一般ヘッダー** | HTTPリクエスト/レスポンス の両方で使用されるヘッダー | Date, Cache-Control, Connection … |
| **リクエストヘッダー** | HTTPリクエストでのみ（クライアント→サーバーでのみ）使用されるヘッダー | Host, User-Agent, Proxy-Authorization, Authorization, Cookie, Referer … |
| **レスポンスヘッダー** | HTTPレスポンスでのみ（サーバー→クライアントでのみ）使用されるヘッダー | Server, Location, Proxy-Authenticate, WWW-Authenticate, Set-Cookie, Strict-Transport-Security, … |
| **エンティティヘッダー** | HTTPリクエスト/レスポンスで使用される、主にエンティティ（実際のデータ）関連情報を含むヘッダー | Content-Type, Content-Length, Allow … |

## 代表的なHTTPヘッダー

| 種類 | ヘッダ名 | 説明 |
| --- | --- | --- |
| 一般ヘッダー | Cache-Control | Webページのキャッシュ期間やキャッシュを許可する対象を示す |
| 一般ヘッダー | Connection | 接続終了時に close するか keep-alive により再利用するかを示す |
| リクエストヘッダー | Host | リクエスト先のFQDN及びポート番号を示す |
| リクエストヘッダー | User-Agent | リクエスト元のブラウザ情報を示す |
| リクエストヘッダー | Referer | リクエストの元になったWebページ（リンク元）のURLを示す |
| リクエストヘッダー | **Forwarded** | リクエスト元の送信元IPやプロトコル等を示す（RFC7239準拠） |
| リクエストヘッダー | **Cookie** | 以前サーバーからSet-Cookieによって受信したCookieを示す |
| リクエストヘッダー | Proxy-Authorization | クライアントとProxyサーバー間の認証方式や認証情報を示す |
| リクエストヘッダー | Authorization | クライアントとWebサーバー間の認証方式や認証情報を示す |
| レスポンスヘッダー | Set-Cookie | サーバーがクライアントにCookieを設定するために使用する |
| レスポンスヘッダー | Proxy-Authenticate | クライアントとProxyサーバー間で認証が必要なことを示す |
| レスポンスヘッダー | WWW-Authenticate | クライアントとWebサーバー間で認証が必要なことを示す |
| レスポンスヘッダー | Strict-Transport-Security | HTTPではなくHTTPSによる接続が必要であることを示す |
| エンティティヘッダー | Content-Type | 含まれるデータの種別を示す |
| エンティティヘッダー | Allow | 対応しているメソッドの一覧を示す |

## X-Forwardedヘッダー

プロキシやロードバランサーを経由すると送信元の情報が隠蔽されるが、X-Forwardedヘッダーを利用することで送信元の情報をWebサーバーにも伝えることができる。標準仕様(RFC7239準拠)として同様の働きを持つ `Forwarded` ヘッダーが用意されているが、X-Forwardedヘッダーの利用率が高い。

| ヘッダー | 内容 |
| --- | --- |
| **X-Forwarded-For** | リクエスト元の送信元IPアドレスが含まれる |
| **X-Forwarded-Host** | リクエスト元が指定していた宛先ホスト（FQDN及びポート番号）が含まれる |
| **X-Forwarded-Proto** | リクエスト元が指定していたプロトコル（HTTPまたはHTTPS）が含まれる |

例）クライアント（送信元IP: 10.0.0.1, Host: sample.com:80）→ プロキシ → Webサーバー の場合、プロキシからWebサーバーへは以下が付与される。

```
X-Forwarded-For: 10.0.0.1
X-Forwarded-Host: sample.com:80
X-Forwarded-Proto: http
```

## Cookie

Webサーバーとブラウザ間で小さなデータをやり取りするための仕組みやそのデータ自体を指す。一般的にはセッションの管理、パーソナライズ、トラッキングといった用途で利用される。

**セッション管理の例:**
1. Webサーバーはユーザーに対してセッションIDを発行し、Set-Cookieヘッダに情報を含めて送信
2. クライアント側のブラウザはリクエストの度にCookieヘッダを提示することでログイン状態を維持

平文でセッションIDをやり取りするのは危険なため、Secure属性の設定が必要。

| Set-Cookie属性 | 意味 |
| --- | --- |
| **Secure** | HTTPS通信の場合にのみブラウザからサーバーにCookieを送信する様に指示 |
| Expires | Cookieの有効期限を指示 |
| Domain | Cookieを送信するFQDNを指示 |
| Path | Domainに加えて `/example` の様なパスを指定する際に使用 |

## 代表的なHTTP認証方式

| 方式 | 内容 |
| --- | --- |
| **Basic認証** | ユーザー名+パスワードを**Base64でエンコード**して送信する認証方式。万が一通信を盗聴された場合、認証情報が復元可能 |
| **Digest認証** | ユーザー名+パスワード+ランダム文字列を**MD5やSHA256でハッシュ化**して送信する認証方式。万が一通信を盗聴された場合、認証情報の復元が困難 |

**HTTP認証の流れ:**
1. クライアント: サーバーまたはプロキシ宛にリクエストを送信
2. サーバー: `WWW-Authenticate` ヘッダでクライアントに認証を要求 / プロキシ: `Proxy-Authenticate` ヘッダでクライアントに認証を要求
3. クライアント: 対向がサーバーの場合には `Authorization` ヘッダで認証情報を応答 / 対向がプロキシの場合には `Proxy-Authorization` ヘッダで認証情報を応答

## 代表的なHTTPバージョン

| バージョン | 特徴 |
| --- | --- |
| **HTTP/1.1** | HTTP 0.9や1.0を改良し、その後長く標準仕様として使われてきたバージョン。テキストでデータをやり取り。**原則HTTPリクエスト/レスポンスを並列的に処理できない** |
| **HTTP/2** | HTTP1.1より高パフォーマンスな通信を実現したバージョン。**バイナリ**でデータをやり取りし、ヘッダーの圧縮機能（HPACK）等も備える。1つのTCPコネクション上で複数のHTTPリクエスト/レスポンスのやりとりが可能（**ストリーム**と呼ばれる単位で識別）。**サーバープッシュ機能**により最初のHTTPリクエストの段階で必要なデータをあらかじめ送信可能 |
| **HTTP/3** | TCPの代わりに**QUIC（UDPベース）**を採用し、HTTP接続の待ち時間短縮を実現したバージョン。TLSの利用にも最適化されているため、初回のネゴシエーションに要する時間も短縮される |

QUIC: UDPをベースにして、TCPの機能（接続の信頼性、データの順序制御、フロー制御など）を組み込んだトランスポートプロトコル。TCPの代わりにUDPを使用することで、接続確立の高速化、遅延の削減、パケットロス時のリカバリーの改善を実現している。TCPでは接続確立に**3-way handshake**（3段階のハンドシェイク）を必要とするのに対し、QUICでは**1ラウンドトリップ**で接続確立と暗号化を同時に行える。
